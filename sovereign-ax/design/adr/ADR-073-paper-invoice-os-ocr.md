# ADR-073 종이 계산서 글자 읽기: OS에 들어 있는 읽기로, 칸 규칙은 폰과 하나로

상태: 제안 (2026-11-28)
근거: 대표 요청(2026-11-28 15:44) "꾸러미에 종이 넣을 때 OS 내장 OCR 이용해서 데이터 채워주면 좋을듯. 그게 다른 목록/합계에도 정리되고." 대표 지시(15:54) "세무사가 어차피 홈택스에서 보는 것들은 안해도 돼." 종이 계산서는 홈택스에 없으므로 꾸러미에 남는다.

## 맥락
- 폰은 종이 세금계산서를 iOS Vision으로 읽고, 칸 규칙(`taxoff-mobile` `src/capture/invoice.ts`)으로 칸을 채워 사장님 확인 뒤 PC로 보낸다(remote-envelope v1.7 `paperInvoice`).
- PC에는 종이 계산서를 올리는 길이 없었다. PC의 글자 읽기는 docparse 샌드박스의 tesseract(ADR-014)뿐이고, 영수증과 사업자등록증에 맞춰져 있다.
- 세금계산서 양식은 빨강이나 파랑으로 인쇄된 표다. tesseract는 표 선이 남으면 칸 글자를 잃는다. 합성 양식 8장(4종, 기울기 0도와 0.8도)을 선을 남긴 채 읽으면 칸을 하나도 채우지 못했다(2026-11-28 Linux 실측).

## 결정

### 1. 칸 규칙은 하나다
- 글자 상자(0~1 비율 좌표)로 칸을 채우는 규칙은 `@sax/remote` `paper-read.ts`(`parsePaperInvoice`)다. 폰의 규칙을 옮겼고, 폰은 vendor 사본을 쓰고 자기 사본을 지운다.
- 칸 규칙은 낱말 상자를 본다. Vision(macOS, iOS)은 줄 하나나 표의 이웃 칸 몇 개를 한 관찰로 내므로("2026 10 28 300,000 30,000", "123-99-45678 등록번호 456-99-12345") 규칙에 넣기 전에 낱말로 나눈다. macOS는 Vision이 낱말마다 준 상자(`boundingBoxForRange`)를 쓰고, 못 받으면 글자 폭 어림(한글 1, 숫자 0.6, 쉼표 0.3)으로 나눈다. 한 관찰에서 나온 낱말은 값을 이을 때 띄어 쓴다.
- 칸 이름의 괄호 꼬리를 잘못 읽은 것("상호" 다음의 "(범인명)")은 상호 값으로 잡지 않는다.
- 세로로 찍힌 "공급자", "공급받는자"는 Vision이 글자마다 상자를 낸다. 같은 세로줄에 쌓인 한 글자 상자는 빼고, 공급받는자 세로줄을 오른쪽 당사자가 시작하는 자리로 쓴다.
- 금액: 작성 줄에서 작성 년 월 일로 읽은 수는 금액에서 뺀다. 세금계산서는 10%가 맞는 두 금액을 먼저 찾고(기운 사진은 작성 줄 여럿을 함께 본다), 없으면 머리 줄 칸 이름(공급가액, 세액) 아래 값을 쓴다. 금액은 칸 오른쪽에 붙어 찍히니 값의 오른쪽 끝으로 칸을 정한다.
- 합계금액은 머리 줄(합계금액, 현금, 수표, 어음, 외상미수금)의 합계금액 칸 아래 값이다. 공급가액 + 세액과 다르면 고치지 않고 확신을 낮춰 둔다(검산이 알린다). 세액을 못 읽었으면 합계에서 공급가액을 뺀 값이 10%에 맞을 때만 세액으로 두고, 공급가액만으로 합계를 짓지 않는다.
- 표 칸이 글자마다 따로 읽히면("상", "호", "(", "법", "인", "명)") 붙인 글이 칸 이름과 같을 때만 한 상자로 붙인다. 지운 표 선이 남아 읽힌 "|", "_", "["는 값에 넣지 않는다. 계산서(면세)는 세액 칸이 없으니 작성 줄의 가장 큰 금액을 공급가액으로 본다.

### 2. PC 읽기 순서
1. docparse 샌드박스가 원본(사진, PDF 첫 쪽)을 풀어 긴 변 2600 이하의 RGB 화소로 다시 그린다(`paperRaster`).
2. main이 그 화소로 무압축 BMP를 직접 써서(머리도 main이 쓴다) OS 글자 읽기에 넘긴다.
   - macOS: Vision `VNRecognizeTextRequest`(ko-KR, en-US, 정확 모드, 언어 보정 끔)를 `osascript -l JavaScript`로 부른다. 한국어는 macOS 13부터다.
   - Windows: `Windows.Media.Ocr`(한국어)를 Windows PowerShell 5.1의 WinRT로 부른다. 스크립트는 `-EncodedCommand`, 그림 경로는 환경변수로 넘긴다.
3. OS 읽기가 없거나(Linux, macOS 12 이하, 한국어 OCR이 깔리지 않은 Windows) 실패하면 샌드박스의 tesseract가 양식 선을 지우고(`cleanFormForOcr`, 빨강과 파랑 글씨는 남김) 낱말을 낸다(`paperWords`).
4. 글자 상자를 1의 칸 규칙으로 채운다.

지키는 것:
- ADR-014: 원본 바이트를 여는 것은 샌드박스뿐이다. OS 읽기는 main이 만든 BMP만 연다.
- OS 읽기 출력은 main이 JSON 모양을 검사해 쓴다(낱말 4000개, 낱말마다 200자, 제어 문자 제거). 모양이 다르면 버리고 tesseract로 간다.
- 시간 상한: OS 읽기 30초, tesseract 90초. 임시 BMP는 0600으로 쓰고 끝나면 지운다.
- 그림과 글은 PC 밖으로 나가지 않는다. 서버를 쓰지 않는다.
- 로그에는 읽기 종류, 낱말 수, 걸린 시간, 실패 이유만 남긴다(`paper.read`, `paper.os_ocr_none`, `paper.os_ocr_failed`). 글은 남기지 않는다.

### 3. 결과는 후보다
- 칸마다 확신값(`fieldConfidence`)이 있다. 화면은 0.8 미만인 칸 이름 옆에 점을 찍는다.
- 매출인지 매입인지는 PC가 내 사업자번호로 정한다(`paperDirection`). 보관용 글자는 참고만 한다.
- 사장님이 확인한 값만 장부에 들어간다.

### 4. 장부와 꾸러미
- 사장님이 확인한 종이 계산서는 `receipts`에 종류(`doc_kind`), 매출과 매입(`direction`), 공급가액, 세액, 승인번호(있으면)를 남기고 확정한다(마이그레이션 v24). 매출인지 매입인지는 폰 값이 아니라 내 사업자번호가 공급자인지 공급받는자인지로 정한다.
- 폰에서 온 계산서는 받자마자 확정한다. 폰 확인 화면의 [보내기]가 사장님 확인이고, PC 검산(`checkPaperInvoice`)이 있고 깨끗하고, 내 번호가 공급자나 공급받는자에 있을 때만이다. 아니면 확정하지 않고 꾸러미가 "확인 필요"로 알린다. 이 판 전에 받은 것은 장부를 읽을 때 같은 규칙으로 확정한다.
- 확정한 종이 세금계산서는 리포트 장부(ADR-072)의 세금계산서 줄로 들어간다. 따로 "종이 계산서" 줄을 만들지 않는다. 그래서 리포트의 매출과 매입, 거래처 순위, 앱 밖 발급, 부가세 어림, 대화의 매출과 매입, 폰 리포트가 같은 숫자를 쓴다. 받을 돈과 낼 돈 건은 아니다(받았는지 모른다): 받을 돈, 받은 돈, 낼 돈에는 들지 않는다.
- 같은 거래가 홈택스 전자세금계산서로 이미 있으면 종이를 세지 않는다. 승인번호가 같거나(전자세금계산서 출력물), 매출 매입과 상대 사업자번호와 작성일과 합계가 같을 때다. 종이 원본은 꾸러미에 그대로 들어간다.
- 종이 계산서(면세)는 확정은 하지만 리포트와 부가세에 넣지 않는다. 면세 전자계산서와 함께 미뤘다(대표 지시 2026-11-28 "면세계산서가 첫 번째로 미룰 기능").
- 영수증 줄(`purchase.receipts`)에는 영수증만 든다. 종이 계산서를 두 번 세지 않는다.
- 꾸러미는 `09 증빙/종이 세금계산서/`에 사진을, `09 증빙/종이 세금계산서.xlsx`에 칸 값을 넣는다(세무사가 홈택스에서 볼 수 없는 자료다).

## 대안
- (a) 기각: 서버 OCR(클라우드 API). 사업자 자료를 밖으로 보내지 않고, 서버를 최대한 쓰지 않는다.
- (b) 기각: tesseract만. 표 양식에서 약하다(맥락의 실측).
- (c) 보류: 네이티브 도우미 실행 파일(Swift, C#). 빌드, 서명, 배포가 는다(ADR-014 대안 (b)와 같은 이유). osascript와 powershell.exe는 OS에 들어 있다.
- (d) 기각: OS 읽기에 원본 파일을 바로 넘기기. OS 그림 풀개가 사용자가 고른 낯선 파일을 열게 된다(ADR-014).

## 결과
- 실측(2026-11-28, Linux, 실제 docparse.mjs를 Chromium에서 돌림, tesseract 길, 합성 8장): 기울지 않은 인쇄 양식 3장(매입, 매출, 계산서)은 모든 칸이 맞았다. 기운 JPEG와 자리마다 칸을 나눈 금액은 상호나 금액 칸이 틀렸다.
- macOS Vision 첫 실측(2026-11-28 맥북, 62263ba, 합성 8장): 글자는 잘 읽었지만(종류, 작성일, 공급자 번호와 상호 8/8) 모든 칸이 맞은 장은 0이었다. 공급받는자 번호 0/8, 공급가액 0/8. Vision이 여러 칸을 한 관찰로 내서 금액이 붙고(공백을 지운 뒤 "20261028300,000…") 오른쪽 사업자번호를 잃었다. 결정 1의 낱말 나누기를 더했다. 두 번째 실측(f302949)도 0/8이었는데, 실측 하네스가 1120x900 창을 1.6배로 키워 CSS 폭 700만 찍어 양식 오른쪽(공급받는자, 세액, 합계)이 잘렸다. 창을 확대 뒤 크기로 키우고 찍힌 그림이 창 전체일 때만 재게 고쳤다. 잘린 실제 Vision 상자로도 작성 년도를 금액으로 읽고(2026), 세로 칸 이름 글자가 값에 붙고("김하늘 급"), 세액을 못 읽은 채 합계를 지어내는 규칙 문제가 보여 위 금액 규칙으로 고쳤다. 잘린 실제 상자에서 보이는 칸은 모두 맞는다. 세 번째 실측(ce569e9, 1792x1024로 양식 전체): 8장 모두 9칸이 다 맞았다. 합성 양식이라 실제 사진은 아직 재지 않았다. Linux에서 Vision처럼 칸마다, 줄 통째, 이웃 두 칸씩 붙인 상자와 칸 이름 오독을 흉내 내 4종에 돌리면 24개 가운데 22개가 모든 칸이 맞는다(틀린 둘은 자리마다 칸을 나눈 금액을 줄 통째로 붙인 것). 맥북에서 다시 잰다.
- 장부(결정 4) 확인(2026-11-28, Linux, 합성 자료로 BankService와 PhoneIntake를 실제로 돌림): 폰 종이 계산서 9장 가운데 내 번호가 있고 검산이 깨끗한 5장이 확정됐다(남의 계산서, 검산 문제, 합계 불일치, 검산 없음은 확정 안 됨). 11월 매출 세금계산서 1,980,000원(종이 1,100,000원과 전자 두 장, 승인번호가 같은 종이는 빠짐), 매입 264,000원(같은 거래 종이와 면세 계산서는 빠짐), 영수증 줄 9,000원, 같은 거래처의 종이와 전자가 한 줄(1,430,000원), 받을 돈은 전자만(880,000원), 부가세 매출 세액 180,000원과 매입 세액 24,000원.
- Windows OCR의 정확도는 아직 재지 않았다. `docparse-e2e`의 `papers`(`SAX_DOCPARSE_E2E=papers`, 글자 상자까지 보려면 `SAX_E2E_TEXT=1`)로 잰다.
- 영문 Windows처럼 한국어 OCR이 없으면 tesseract로 떨어진다. 한국어 Windows 11(ADR-008)에는 한국어 OCR이 들어 있다고 보지만 추정이고, 실기에서 `paper.os_ocr_none`이 남는지로 확인한다.
